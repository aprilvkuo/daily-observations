**一句话理解：HarnessMM 并不是把 Agent 的每一次思考压缩得更短，而是把已经决定好的下一步存成“可执行的条件动作”，在条件满足时直接执行，省掉多余的一次大模型调用。**

> 原论文：[HarnessMM: Recursive Self-Improvement for Harness Token Efficiency](https://arxiv.org/abs/2610.32813v1)（2026-10-23，v1）；[HTML 全文](https://arxiv.org/html/2610.32813v1)。本文解读日期：2026-10-29。作者：Yuhua Jiang、Chang Xu、Feifei Gao、Li Zhao。

## 一、Agent 真正浪费的，未必是每次想得太多，而是重复想已经决定的事

想象一个开发者已经决定：“先修改代码，再运行测试；测试通过就执行已经写好的下一条命令。”可是每完成一个动作，系统都要重新请他开会讨论：下一步该做什么？

典型工具型 Agent 有类似结构：**LLM 推理 → 工具执行 → 读取结果 → LLM 再推理**。工具返回后，确实可能出现新信息，需要重新判断；但也可能只是确认了一个早已约定好的条件，例如“测试退出码为 0”。

常见的降本方法是缩短 Prompt、裁剪历史、减少思考 Token，或者换一个更小的模型。HarnessMM 的问题更往前一步：**如果下一步的动作及参数早已决定，我们为什么还要调用模型？**

论文将这一矛盾称为计算替代问题。一个替代动作必须真的取代原本的慢速推理调用，而不能只是在原调用之外额外执行了一个“小模型判断”。这也是作者提出“Substitution Paradox（替代悖论）”的动机（[论文 §3](https://arxiv.org/html/2610.32813v1)）。

## 二、关键不是缓存答案，而是把“已确定的动作”和“尚待发生的条件”拆开

HarnessMM 的核心由三个机制组成：

**1. EDG：Executable Decision Graph，可执行决策图。** 慢速 Actor 先做真正需要语义判断的工作，并把可以提前决定的后续动作写进图里。每个节点记录固定的工具名和字面参数、前置依赖、基于公开结果的 Guard。图内不能预填尚未知道的动态参数。它不是“把上一段 CoT 贴回 Prompt”，更像一个带条件的小程序。

**2. GDR：Guarded Decision Reuse，受条件约束的决策复用。** 执行工具后，控制器读取真实回执（receipt），检查前置节点是否完成、Guard 是否通过、参数是否已经封闭。只有三个条件都满足才允许执行图中的动作。动作图可以跨越多次工具调用而持续保留；信息不充分时交还原 Actor。

**3. CCS：Certified Callback Substitution，可审计的推理调用替代。** 被激活的动作通过原生工具接口执行，并记录图哈希、节点 ID、准确参数、前置与工具回执，以及被跳过的慢速回调 ID。这样可以证明“这次确实执行了预先确定的动作，且相应的模型调用没有发生”。但这个证书**只证明结构替代，不证明业务动作正确**（[论文 §4.1–4.3、Appendix D](https://arxiv.org/html/2610.32813v1)）。

~~~mermaid
flowchart TD
  A["原 Actor：推理并生成动作图 EDG"] --> B["执行第一个工具动作"]
  B --> C["获取真实工具回执"]
  C --> D{"前置依赖、Guard、参数都满足？"}
  D -- 是 --> E["GDR 复用已有动作"]
  E --> F["CCS：原生执行并记录跳过的回调"]
  F --> C
  D -- 否 / 不确定 --> G["回到原 Actor 重新推理"]
  G --> B
~~~

例如提前写好 `pytest tests/test_api.py`，且明确规定“前一步文件写入成功才运行它”，那么写入成功的回执可以触发这条命令。相反，如果测试失败后需要从错误日志**推导**一个未知的修复方案，就必须重新调用 LLM；不能拿旧动作假装已经理解新问题。此例用于解释机制，并非论文中逐字出现的运行轨迹。

论文中的编码适配器让慢速 CoT Actor 生成有限的动作 bank。快速选择器只能输出已存在的候选 ID 或弃权，不能发明新命令、不能修改参数；它使用同一 DeepSeek backbone 的关闭推理模式，以极短的选择输出控制执行。空候选、解析失败、Guard 不成立时回退到原始慢速路径（[Appendix C.4](https://arxiv.org/html/2610.32813v1)）。

## 三、RSI 改进的是 Harness 的决策边界，而不是模型权重

标题里虽然有 Recursive Self-Improvement，但这里**没有自我训练大模型参数**，也不是一个无限制改写代码的自主进化系统。

它保留原 Actor、工具和评测器，用训练任务反馈迭代调整 Harness 的配套配置，例如动作图生成规则、提示词、上下文与适配器。用相互分离的验证任务选择候选，再冻结配置做最终测试。部署时，在线控制器只是在“执行已授权的确定动作”和“退回原 Actor 推理”之间选择（[论文 §4.4、§5.1、Appendix B](https://arxiv.org/html/2610.32813v1)）。

~~~mermaid
flowchart LR
  A["训练任务和执行反馈"] --> B["Optimizer：提出 Harness 配置修改"]
  B --> C["独立验证：成功率与完整 Token 成本"]
  C --> D["冻结选中的配置"]
  D --> E["原 Codex / DeepSeek Harness + EDG/GDR/CCS"]
  E --> F["新任务真实执行"]
~~~

这里有两种不同尺度的复用：**单次任务内复用决策图**，以及**跨训练迭代选择更优 Harness 配置**。前者是核心执行机制，后者才是本文限定意义上的 Harness RSI；不能将两者混为一谈。

## 四、实验最有说服力的部分，是固定底座后比较整次任务的成本

作者把 HarnessMM 接入现有 Codex 与 DeepSeek Harness，而非重新打造一个 Coding Agent。评估保持每个对比组内的底座模型、工具和评分器一致；报告整个任务中付费模型调用的输入与输出 Token，连同动作图生成、快速选择、失败和回退成本，而不是仅估算被省略的单次调用（[论文 §5.1–5.3、Table 1](https://arxiv.org/html/2610.32813v1)）。

| 测试及 Harness | 原成功率 → 新成功率 | 原 Token/任务 → 新 Token/任务 | 节省 |
|---|---:|---:|---:|
| HumanEval 98题，Codex | 90.82% → 90.82% | 66.72k → 47.02k | **29.54%** |
| HumanEval 98题，DeepSeek Harness | 71.43% → 85.71% | 96.28k → 11.62k | **87.93%** |
| MBPP-sanitized 257题，Codex | 91.83% → 90.66% | 129.55k → 49.22k | 约 62.0% |
| MBPP-sanitized 257题，DeepSeek Harness | 90.27% → 91.83% | 53.98k → 10.61k | 约 80.3% |

同一组 HumanEval 中，DeepSeek Harness 的付费调用总数从 954 降至 415，记录到 **147 次有证书的慢速回调替代**；Codex 从 524 降至 499，记录 **18 次替代**。两者不是一一对应：完整 HarnessMM 集成还同时改变了上下文管理和最终答复方式，因此**不能把 87.93% 的总节省全部归因于 GDR 或 CCS**。而且 Codex 在 MBPP 上成功率实际下降了 1.17 个百分点，说明省钱与性能保持必须分别检查（[论文 Table 1、§5.3、Appendix F](https://arxiv.org/html/2610.32813v1)）。

更直接的消融来自 DeepSeek Harness 的另一组 MBPP 测试，257 个测试任务、固定相同设置：

| 条件 | 成功率 | Token/任务 |
|---|---:|---:|
| 完整 HarnessMM | 93.77% | **13.17k** |
| 去掉 GDR：图只复用一次 | 93.00% | 18.03k |
| 去掉 CCS：保留慢速回调 | 93.39% | 16.37k |
| 禁止执行 EDG | **95.33%** | 16.19k |

这说明持久化决策复用相对单次使用节省 **26.91%** Token，替代慢速回调相对保留回调节省 **19.52%**。但禁止 EDG 执行的条件反而多解出 4 道题；不同条件间质量差异的置信区间包含零，不能宣布“复用动作保证提高正确率”。另一个更早的消融版本甚至出现 GDR 复用更多却成本略高的结果，说明测量与控制设置很关键（[论文 §5.5、Appendix E，Table 3–6](https://arxiv.org/html/2610.32813v1)）。

## 五、不是所有任务都适合跳过推理：要看可复用动作的密度

论文的负面结果非常有信息量。

在 AIME 的 560 道测试题上，HarnessMM 达到 87.14% 正确率、5.90k Token/题，但成本比 No Skill **高 28.34%**，比 AutoSaddler **高 20.44%**。数学推理的输出成本占比很高，而新增的上下文和配置生成成本不一定能抵消掉。

在历史 Terminal-Bench 开发任务中，也有 Token 大降、成功率明显下降的组合。更重要的是，论文记录了一个 CoT/Jev 配套执行方案：虽然 94.44% 的 episode 都有经过验证的快速动作，但整次任务成本仍比原 Harness **高 127.07%**，成功率低 7.29 个百分点。这一反例足以说明：**“用了快速选择器”和“真正减少了总成本”完全是两回事**（[论文 §5.4、Appendix D.8](https://arxiv.org/html/2610.32813v1)）。

MiniWoB++ 的八轮训练引导实验中，32 个训练任务的成功率从 34.38% 升到 90.63%，Token/任务从 3.26k 降至 1.06k。第八轮与单次使用图的对照同为 29/32，持久图节省约 29.83% Token。不过这是**训练迭代曲线**，不能直接当成独立测试集上连续自我进化的证明（[论文 §5.6、Figure 5](https://arxiv.org/html/2610.32813v1)）。

论文将优化开发成本与部署执行成本分开记账。对于部署 N 个任务，应考虑：

**摊销后的平均成本 = 优化与验证开发成本 / N + 单次实际执行成本。**

只有任务足够多、可确定动作足够频繁、Guard 与快速选择的开销足够小，真实节省才可能覆盖引入这一系统的成本。论文主要报告的是模型 Token，**不等于已证明端到端延迟、硬件能耗和实际 API 账单同比例下降**（[论文 §4.4、§6](https://arxiv.org/html/2610.32813v1)）。

## 六、对通用 RSI Optimization System：值得新增“推理调用优化”，而不是重造 Agent

如果采用 **Solver / Evaluator / Optimizer** 三层架构，我会把这篇论文视为优化空间的扩展，而不是替代 Harness²：

| 角色 | 应该负责什么 |
|---|---|
| Solver | 继续运行 Codex、Claude Code 或 DeepSeek Harness 等成熟执行器；通过适配器暴露工具回执与调用边界 |
| Evaluator | 同时核算任务正确性、工具回调替代次数、完整 Token 成本、失败回退和多轮稳定性 |
| Optimizer | 优化 Prompt、工具使用规则、上下文策略，以及**哪些已确定的动作可以跳过重复推理** |
| 受控执行层 | 存储 EDG、检查真实 Guard、执行字面动作、记录 CCS 证据；不允许 Selector 修改工具参数 |

与 Harness² 的关系可以理解为：

- **Harness²：** 改进“Agent 应该遵循什么工作方法”，重点在优化和积累 Harness 改进经验。
- **HarnessMM：** 改进“什么时候真的需要再调用一次模型”，重点在安全条件下替代冗余的推理回调。

工程落地建议从一个非常窄的 Coding 场景开始：选取命令及参数事先完全确定的连续工具动作；只启用公开、可判定的 Guard；记录每次 Actor callback 的 ID 与实际 Token；出现未知结果就退回原执行器。先做 **Shadow Mode（只记录可替代动作，不真的跳过）**，再在可回放测试集中比较开启和关闭替代的效果。这是面向工程实现的推论，不是论文已经验证的一整套通用部署方案。

最后保留三个边界。**第一，Guard 成立不等于动作正确**；错误的预先规划可能被原样执行。**第二，适配器和条件语义具有场景依赖**，不可能用一个通用的文件存在检查覆盖所有业务状态。**第三，节省是质量约束下的优化结果，不是无条件追求最少 Token**。对于开放式探索、诊断未知错误和高不确定性任务，重新推理仍然是合理且必要的。

## 七、结论：RSI 的一个务实方向，是让 Harness 学会“不再重复思考”

HarnessMM 最值得借鉴的不是夸张的节省百分比，而是一个可以验证的工程分离：**由 LLM 负责新决策，由程序负责执行已决策且条件满足的部分，并用完整任务结果判断优化是否值得。**

它也提醒我们：有 Harness 改写不等于性能改进，有快速动作不等于总成本下降，有替代证书也不等于任务正确。真正成熟的 RSI 系统，需要把这三种证据严格区分。
