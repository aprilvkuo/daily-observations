> **核心判断：**OpenRSI 不是一个单一的代码进化脚本，而是把机器学习工程变成可验证的 AI4AI 训练场。其方法论贡献是让环境、模型训练与长时搜索共用一套明确的“代码修改动作”。

## 为什么需要它

单纯把 Kaggle 任务交给 Coding Agent，Agent 能写训练代码，却很难积累可靠的跨任务改进能力。原因包括环境构建不一致、打分器不可靠、错误轨迹被当作学习经验，以及 Solver 与搜索器没有共享动作语义。OpenRSI 尝试把这些独立工程问题组织成完整实验链路。

## 它如何运行：让改进可回溯

**OpenMLE-Gym** 提供任务、隔离运行环境与可验证评测；**OpenMLE-RL** 从有执行反馈的轨迹里训练操作能力；**OpenMLE-Evo** 在推理阶段保存和演化候选程序。Frontis-MA1 将修改归纳为 **Draft（从零写）/ Improve（优化）/ Debug（修复）/ Crossover（组合）** 四种算子，训练和推理共用这套接口。

```mermaid
flowchart LR
 A[可验证任务 Gym] --> B[四种演化操作]
 B --> C[运行并打分 Evo]
 C --> D[经验轨迹]
 D --> E[训练模型 RL]
 E --> B
```

这里有两个时间尺度：**任务内**是不断写和评测程序；**跨任务**是利用轨迹训练更好的代码演化模型。论文的实验不意味着每次比赛都在线微调权重。

## 实验报告到底证明什么

在作者报告的 **MLE-Bench Lite、12 小时/任务、单张 RTX 4090 且限制 12GB 显存**条件下，Frontis-MA1（35B）结合 Evo 的 Medal Average 从 **39.39%** 提升到 **60.61%**，加入经验先验和异步搜索的 Evo-Max 报告 **71.21%**。在独立 NatureBench Lite 上，固定搜索框架仅换训练模型，Match-SOTA 从 **50%** 到 **70%**；固定模型仅换演化框架，从 **20%** 到 **50%**。这些分别衡量模型训练与系统设计的贡献，指标不能混用。[论文摘要与实验](https://arxiv.org/abs/2607.28568v1)。

## 关键局限与反证

这不是对“无限 RSI”的证明。不同系统的模型和预算可能不同；同一任务多次试验会过拟合本地分数；开源模型和代码不代表依赖、数据资产、任务验收均已低成本可重现。仓库的 **CC BY-NC 4.0** 对商业使用也有限制，需要单独审核。

## 对 Kaggle RSI System 的启发

你现有的 Kaggle Adapter 可保留任务输入、运行命令、状态查询和结果输出四个边界，把 OpenMLE-Evo 视为完整 RSI System 黑盒，而不是把它拆成一个 Solver。先验证“无需优化、仅复现公开基线”的提交链路，再启用四类改进动作。每个候选要有数据版本、程序 hash、验证集、提交回执和预算记录，否则模型训练会学到不可复现的噪声。
